4xx and 5xx are intentionally not summed. 4xx responses are often normal: 401 from authentication, 404 from non-existent paths, 403 from active WAF rules. What indicates an issue needing attention is 5xx, as it signifies server failure. The daemon never sends anything itself. It only writes to a queue table; a separate script sends it from a systemd timer every 10 seconds. That separation is deliberate: one slow webhook would otherwise hold up log reading, and the daemon reads logs every two seconds, so a single unresponsive address could make ZySentinel stop seeing attacks entirely.
Failed notifications are not deleted. They are retried on the next cycle until the retry limit is reached, so a temporary network outage does not lose alerts. After the limit, the row stays visible in the table above but is no longer attempted.
NOTIFY_TOKEN is never shown on this page and never written to the log. Only whether it is set. The token file is mode 600 for the same reason it behaves like a password.

This queue does not block anyone. An IP in this list is only recorded; its packets still pass normally. This is the middle ground between "block nothing" and "block everything over the threshold": you can see who would be blocked, then decide one by one.
Approve blocks the IP immediately, same as pressing Block Now in the Blocked IPs tab. Dismiss releases it from the queue and it is never blocked. A dismissed IP can be queued again later if its score rises high enough, so dismiss only IPs you are sure are not attackers.
The queue only fills while blocking mode is off. The threshold is review_score in guardd.conf; set it to 0 to turn the queue off entirely.
